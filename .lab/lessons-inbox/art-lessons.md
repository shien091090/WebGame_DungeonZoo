# 美術經驗提案(大場面動物園 polish-1, 美術節點)

## 提案 1 — 放進「語意一致」分類(新經驗, 掛 P3、P4)

- 從另一款遊戲移植現成的物件畫法, 原款的字典詞跟著搬進來, 和本款的字典撞在一起(大場面動物園 polish-1 建置設計判斷, 非老闆回饋, 不算升格證據: 規格把 A、C 兩款的爆炸桶、回復泉、草叢、果樹抽成參考檔, 要 B 款美術移植。照搬的話, 草叢的葉尖三角在 B 款是「尖角 = 危險」; 回復泉的青色水和同一座地下城的 1 號傳送陣同一個色名; 果樹「可打」的提示用白色虛線, B 款的「你打得到」卻是金色虛線) → 移植時只確認物件本身讀得懂, 沒拿本款的形狀語言、保留色, 以及**同一場景裡會一起出現的物件**重新對過; 參考檔的畫法本來就是為原款字典設計的 → 移植任何外來畫法時, 逐項列出它用到的形狀(尖角、虛線、圓環)與顏色, 拿本款 style.md 的形狀語言與色票查: 撞到保留詞就換成本款的對應詞(該作: 葉尖改圓葉、果樹提示改用本款「打得到」的金虛線); 顏色再和同一場景會同框的物件比色名, 撞到就移色名並另加形狀通道(該作: 泉水移到天藍、主通道改成石盆 + 紅心)。在 style.md 色票表下寫明最難分的那一幀(待製作人驗收)〔P3〕〔P4〕

## 提案 2 — 放進「交付自查」分類(新經驗, 不掛理念: 屬分工)

- 介面用「第 N 項」描述陣列裡要亮起的那一格, 沒寫陣列是 0 起算還是 1 起算(大場面動物園 polish-1 建置設計判斷, 非老闆回饋: 日曆的 log 註明「第 i 項是第 i+1 天」, 同一段又寫「day 那格(第 day 項)要亮起」; 照 0 起算讀會亮在明天那格, 照 1 起算才是今天) → 介面作者混用「第 i 項 = 索引 i」和口語的「第幾個」, 美術和 RD 同時開工, 各自猜各自的 → 開工對介面時, 逐一檢查每個「第 N 項 / 第 N 個」的描述, 確認它是索引還是序數; 不確定就照規則的意思選(該作: 亮今天那格 = index day − 1), 在 style.md 判讀約定寫明算法, 並在回報請製作人把「索引從 0 起算, 第 N 天 = index N − 1」寫進介面, 列為出介面必查項(待製作人確認)
